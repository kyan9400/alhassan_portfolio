At Junzi Tech I worked on a Node.js / Express service backed by MongoDB, with a React front end on top.
One endpoint sat on a critical path of the product, so its latency was felt directly by users. I reduced its average response time by about 60% without changing its response
contract. This note is the decision log behind that change. The code is not mine to share, so the snippets
below are generic shapes that illustrate the technique, not the production code.

## Context

The endpoint returned a list of records plus a few related fields that the UI needed to render a view.
Over time it had grown the way endpoints usually grow: one more field here, one more lookup there. Nobody
had broken it; it had simply accumulated work.

Two constraints shaped every decision that followed:

- **The response contract could not change.** The front end depended on the exact shape of the JSON. A faster endpoint that returned something slightly different would have been a
  regression, not an improvement.
- **The data changed during the day.** Some of it was read far more often than it was written, but it was not
  static, so "just cache it for an hour" was not an option.

## Options I considered

### Option 1: put a cache in front and move on

This is the tempting one. A cache hides a slow query very well on a hit. But on a miss the user still pays
the full cost, and misses happen after every invalidation, every deploy and every cold start. A cache over a
slow query also makes the slow query harder to see, because average numbers improve while the worst requests
stay just as bad.

### Option 2: scale the database or the service

More resources would have helped a little, but the problem was not capacity. The query did more work than it
needed to, and more hardware would only make that waste cheaper for a while.

### Option 3: fix the query first, then add a cache

Make the uncached path fast and predictable, then add caching where the read-to-write ratio justifies it. This
is slower to deliver than option 1, but every later decision rests on a path I understand.

## Decision

I chose option 3, in that order. The query refactor came first and shipped on its own, so I could see its
effect in isolation. The cache came second.

### Step 1: measure and read the query plan

Before changing anything I looked at what the database was actually doing. In MongoDB that means running
the query with `explain("executionStats")` and comparing documents examined with documents returned. When
the database reads far more documents than it sends back, it is not using an index for that filter.

The fixes were the ordinary ones, applied carefully:

- a **compound index** whose field order matches the equality filters first, then the sort;
- a **projection**, so the database returns only the fields the response needs instead of whole documents;
- removing **per-item lookups** in application code (the N+1 pattern) and fetching related data in one
  batched query instead.

```js
// Generic example: filter + sort served by one compound index,
// projection limited to the fields the response actually uses.
await db.collection("items").createIndex({ accountId: 1, status: 1, updatedAt: -1 });

const items = await db
  .collection("items")
  .find(
    { accountId, status: "active" },
    { projection: { _id: 1, title: 1, status: 1, updatedAt: 1, ownerId: 1 } }
  )
  .sort({ updatedAt: -1 })
  .limit(50)
  .toArray();

// One batched lookup instead of one query per item.
const ownerIds = [...new Set(items.map((i) => String(i.ownerId)))];
const owners = await db
  .collection("owners")
  .find({ _id: { $in: ownerIds.map(toObjectId) } }, { projection: { name: 1 } })
  .toArray();
```

### Step 2: protect the response contract

Because the shape could not change, I treated the old response as the specification. Before and after the
refactor I compared responses for the same inputs, field by field, including ordering and empty cases. The
mapping from database documents to the response lived in one function, so a change in the projection could
not quietly drop a field somewhere else.

### Step 3: add a cache-aside layer

Only after the uncached path was fast did I add caching, and only for the part of the data that is read much
more often than it changes. I used the cache-aside pattern: read from the cache, fall back to the database on
a miss, write the result back with a TTL, and delete the key when the underlying data changes.

```js
// Generic cache-aside wrapper with a TTL and explicit invalidation.
async function cached(key, ttlSeconds, load) {
  const hit = await cache.get(key);
  if (hit !== null) return JSON.parse(hit);

  const value = await load();
  await cache.set(key, JSON.stringify(value), { EX: ttlSeconds });
  return value;
}

const listKey = (accountId) => `items:list:${accountId}`;

// Read path
const payload = await cached(listKey(accountId), 60, () => buildItemsResponse(accountId));

// Write path: invalidate after the database write succeeds
await db.collection("items").updateOne({ _id }, { $set: changes });
await cache.del(listKey(accountId));
```

The TTL is a safety net, not the main invalidation strategy. Explicit deletes on write keep the data fresh;
the TTL limits the damage if a write path ever forgets to invalidate.

## Trade-offs

- **Delivery time.** Fixing the query took longer than adding a cache would have. I think it was the right
  price, because it made the miss path fast as well.
- **Index cost.** Every index speeds up some reads and slows down every write to that collection, and it takes
  memory. I added only the index the query plan asked for, not one per field.
- **Cache consistency.** Cache-aside means a short window where a reader can see stale data if an
  invalidation races with a read. For this data that was acceptable; for balances or permissions it would not
  be.
- **More moving parts.** A cache is one more thing to monitor, and one more thing that can be down. The
  endpoint had to keep working, only slower, if the cache was unavailable.

## Lessons

### Read the plan before you write the fix

Most of the improvement came from things the query plan pointed at directly: a missing compound index, whole
documents being returned, and a loop of small queries. None of it needed clever code.

### Cache a fast path, not a slow one

A cache on top of a slow query improves the average and leaves the worst requests untouched. A cache on top
of a fast query makes a good path better, and a miss is no longer a problem.

### The contract is part of the performance work

Keeping the response identical is what made the change safe to ship. Comparing old and new responses for the
same inputs took little time and removed the main risk of the whole exercise.

### Invalidation belongs next to the write

Keeping the cache key builder and the invalidation next to the write code made it hard to forget. If I did it
again, I would add a test that fails when a write path changes the data without deleting the matching key.
