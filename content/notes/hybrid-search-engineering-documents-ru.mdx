С января 2026 года я работаю в «Электросервисе» в Москве над поиском по инженерной документации: PDF, Word,
Excel и отсканированные документы. Инженеры задают вопросы естественным языком, но так же часто ищут точные
коды оборудования, артикулы и ссылки на нормативы. В этой статье расскажу, почему в итоге получился гибридный
поиск (ключевые слова плюс плотные векторы в FAISS), а не чисто векторный. Система и данные под NDA, поэтому
всё описание остаётся на уровне техник.

## Контекст

Инженерные документы не похожи на статьи в блоге. В одном файле могут соседствовать текст, таблицы, чертежи
с подписями и длинные списки обозначений. Вопросы пользователей делятся на два очень разных типа:

- **Описательные вопросы**, например как защищён от перегрузки определённый тип оборудования. Ответ в
  документе сформулирован иначе, чем вопрос.
- **Точный поиск**: конкретный артикул, код изделия или пункт стандарта. Полезна только точная строка, а
  «похожая» строка — ошибка.

Поиску, который справляется только с одним из этих типов, пользователи быстро перестают доверять.

## Какие были варианты

### Только ключевые слова (BM25)

Лексическое ранжирование быстрое, объяснимое и отлично работает с точными токенами. Но оно проваливается на
перефразировании: если в документе написано «тепловая защита», а пользователь спрашивает про «перегрев»,
пересечения слов может не хватить.

### Только векторный поиск

Модели эмбеддингов из sentence-transformers хорошо справляются с перефразированием, а FAISS делает поиск
ближайших соседей по большому числу чанков дешёвым. Но плотные векторы кодируют смысл, а не точную
последовательность символов. Два артикула, отличающиеся одной цифрой, могут оказаться очень близко в
векторном пространстве, и у модели нет причин предпочесть точный. Для инженера это худший вариант ошибки:
уверенный, правдоподобный и неверный результат.

### Гибридный поиск

Запускать оба поиска по одним и тем же чанкам и объединять результаты. Лексический поиск держит точные
обозначения, векторный закрывает описательные вопросы. Цена — больше компонентов и отдельный шаг слияния,
который нужно продумать.

## Решение

Я выбрал гибридный поиск; загрузка документов и обработка запросов реализованы как сервисы на FastAPI.
Конвейер состоит из четырёх этапов.

### OCR до индексации

Отсканированная страница — это картинка. Без OCR она ничего не даёт ни одному индексу, и поиск молча ведёт
себя так, будто этих документов нет. Поэтому извлечение текста — первый этап загрузки, а не доработка на
потом:

- из PDF, Word и Excel текст извлекается напрямую;
- страницы без текстового слоя проходят через OCR;
- результат нормализуется (пробелы, переносы на концах строк, типичные ошибки распознавания) до разбиения
  на чанки.

Нормализация важнее всего для обозначений. Если OCR прочитал ноль как букву O, точный код превратился в
другой код, и никакой трюк на этапе ранжирования это уже не исправит.

### Чанкинг с метаданными

Документы делятся на чанки: достаточно маленькие, чтобы эмбеддинг был качественным, и достаточно большие,
чтобы мысль не рвалась. Таблицы и строки электронных таблиц по возможности не разрезаются, потому что
иначе артикул отрывается от своего описания. У каждого чанка есть метаданные:

```python
# Условная структура проиндексированного чанка
chunk = {
    "id": "doc-123#p4#c2",
    "text": "...",
    "source": "doc-123",
    "file_type": "pdf",
    "page": 4,
    "section": "3.2 Уставки защиты",
    "ocr": True,
}
```

Метаданные решают две задачи: позволяют фильтровать (по документу, по типу) и делают каждый ответ
прослеживаемым до файла и страницы.

### Лексический и векторный поиск рядом

Одни и те же чанки попадают в два индекса: лексический для ранжирования в духе BM25 и индекс FAISS с
эмбеддингами sentence-transformers. При запросе работают оба, и каждый возвращает свой топ.

Токенизатору для лексической части нужно уделить внимание. Стандартный токенизатор может разбить код вроде
«AB-1200/3» на фрагменты, которые совпадут с половиной корпуса. Сохранение токенов, похожих на обозначения,
целиком (в дополнение к обычным токенам) и делает точный поиск надёжным.

### Слияние через reciprocal rank fusion

Оценки BM25 и косинусная близость живут в разных шкалах, поэтому складывать их напрямую бессмысленно без
аккуратной калибровки. Reciprocal rank fusion обходит эту проблему, используя только ранги:

```python
# Условная реализация RRF по нескольким ранжированным спискам id чанков
def rrf(result_lists, k=60):
    scores = {}
    for results in result_lists:
        for rank, chunk_id in enumerate(results, start=1):
            scores[chunk_id] = scores.get(chunk_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

merged = rrf([keyword_ids, dense_ids])
```

Чанк, который высоко в обоих списках, поднимается наверх; чанк, найденный только одним из поисков, всё
равно получает шанс. Метод простой, не требует обучающих данных, и по нему легко разобраться, почему
результат выглядит странно.

### Ответы с опорой на найденные фрагменты

Когда система формирует ответ, а не список, ответ строится только из найденных фрагментов, и каждое
утверждение ссылается на свой чанк: файл, страницу, раздел. Если во фрагментах ответа нет, правильный вывод —
«в документах не найдено», а не догадка. Для инженерных данных «не знаю» со ссылками полезнее гладкого
абзаца без источников.

## Компромиссы

- **Два индекса нужно синхронизировать.** Каждое обновление документа должно дойти и до лексического
  индекса, и до FAISS, а частичное обновление даёт запутанные результаты. Загрузка должна обрабатывать
  индексацию документа по принципу «всё или ничего».
- **Больше задержка на запрос.** Два поиска и слияние дороже одного. Впрочем, этапы поиска обычно дёшевы
  по сравнению с OCR и построением эмбеддингов, которые выполняются один раз при загрузке.
- **OCR задаёт потолок.** Поиск не может быть лучше извлечённого текста. Плохие сканы ограничивают все
  последующие этапы, поэтому нормализации уделяется не меньше внимания, чем ранжированию.
- **RRF теряет силу оценок.** Метод не учитывает, насколько уверен был каждый поиск. Для старта это
  разумно, а взвешенный вариант можно рассмотреть, если один из поисков стабильно надёжнее для какого-то
  типа запросов.

## Выводы

### Точные строки — требование первого класса

В инженерной документации обозначение часто и есть весь вопрос. Любая архитектура, которая считает его
просто ещё одной семантикой, провалится именно на тех запросах, которые важнее всего.

### Качество загрузки определяет качество поиска

OCR, нормализация и границы чанков дали для качества результатов больше, чем любые изменения в ранжировании.
Если результат неверный, первым делом стоит смотреть на проиндексированный чанк.

### Каждый ответ должен быть прослеживаемым

Метаданные у каждого чанка сделали возможной отладку и позволили проверять ответы. Инженер доверяет
результату, который можно открыть на нужной странице.

### Начинать слияние с простого

Reciprocal rank fusion — хороший первый выбор, потому что даёт разумный результат без настройки. Всё, что
сложнее, должно доказать своё преимущество в сравнении с ним.
